# Local knowledge storage

`src/knowledge/` provides local storage, deterministic qualification, confirmed model writes, explicit personal pack installation and a resumable HTTP sync engine. The terminal supports local browsing, confirmed edits and explicit sync selection; the runtime reuses the selected MCP authorization and loads frozen session preferences. Desktop knowledge pages and authorized sharing remain unfinished. Existing `MEMORY.md` files and skills are unchanged. The unfinished integration is listed in [Known issues](../known-issues.md#local-knowledge-and-personal-sync).

## Protocol mirror

The versioned JSON schemas in `src/data/knowledge-sync/v1/` come from Circle Hub's `personal-sync@1` contracts. The adjacent `provenance.json` records the source repository, committed source `eef4ca121fa673a8067d32d74c05f923a93fd42b` and exact file digests. All mirror inputs come from that commit, including `contracts/src/spaces.ts`; no working-tree observation is used. The original sources and local adaptations are separately pinned. Circle imports no Hub service, database or business runtime.

The original shared vectors are copied without modification into `tests/fixtures/knowledge-sync/v1/`. They pin exact canonical UTF-8 bytes, IDs and route definitions. The vectors describe merge and transport expectations; they do not establish live merge, authentication, purge or server atomicity.

```sh
# Check the pinned mirror without a Hub checkout.
npx tsx scripts/verify-knowledge-sync.ts
# Also compare every recorded input with an explicit, read-only upstream checkout.
npx tsx scripts/verify-knowledge-sync.ts --upstream ../circle-hub-sync
```

Run the explicit upstream check at the start of every implementation stage. Refresh only from a committed Hub state and record its commit; a changing, dirty Hub checkout is never a refresh source. A missing or changed explicit upstream fails. Offline mode reports zero upstream comparisons; it cannot detect unseen upstream changes. Do not regenerate expected bytes from the encoder to accept a mismatch. A protocol update must review the contract, refinements, original vectors and provenance together.

Ajv validates the mirrored schemas without coercion, defaults or removal of unknown fields. Additional checks preserve the source contract's Unicode, UTF-16 field lengths, canonical base64, sorted sets, unique batches, registered errors, pack paths/dependencies and checked-purge rules, which JSON Schema alone does not express. This adds no dependency.

Editable strings remove one leading BOM, change CRLF/CR to LF and normalize to NFC. Other whitespace stays significant. Object keys sort by UTF-16 code units; array order changes only when callers explicitly construct a contract-declared set. Duplicate JSON members, normalized key collisions, malformed UTF-8/Unicode, non-JSON values and altered or noncanonical object bytes are refused.

Source and quotation bytes stay in base64 byte objects and are not normalized. The source's `raw_sha256` describes its original assembled bytes; the object ID describes a typed canonical envelope. Neither ID is a Hub `src:`, `tree:` or `rec:` reference or a grant of access.

## Separate local store

`new KnowledgeStore(home)` requires an explicit runtime home. It creates `knowledge/knowledge.sqlite` and private `knowledge/objects/` inside that home, and never opens `circle.sqlite`. Terminal and desktop homes therefore have separate clients. The persistent random client ID survives reopening; item IDs supplied in revisions survive renames and moves.

The database uses its own application ID, append-only migration sequence and `user_version`. A newer version or an unrelated populated database is refused before changing its version or enabling WAL. Files have mode 0600 and directories 0700 on Unix. SQLite runs with foreign keys, WAL and FULL synchronous writes. No existing memory or skills directory is migrated or uploaded.

`put` / `putBatch` validate and stage immutable objects. The writer holds a database write transaction while publishing a same-directory temporary file, syncing it and atomically renaming it, then registering the object. A local batch is bounded to 64 objects and 8 MiB of encoded bytes; source uploads need multiple batches. Sharing violations during rename get at most four retries; other errors fail immediately. This is filesystem recovery, not a retry of a failed sync operation.

Staged objects do not enter search or current browsing. `commit(snapshot, expectedHead)` validates the complete reachable object graph and uses a local compare-and-exchange. Revisions, current projection, FTS and current head change in one transaction. Omission cannot delete an existing item: deletion requires its own revision and parents. Old object bytes remain readable. Conflicting heads have no selected search body, and a resolution must descend from every previous head.

Graph checks cover typed dependencies, revision identity, explicit deletion parents, duplicate item IDs across pages, source size/hash, directory cycles and NFC path collisions. A directory inventory has one current root; canonical empty and pack-only inventories need no invented directory. Source verification streams chunks; the graph keeps at most 8 MiB of object bodies cached. Graph traversal is bounded to 100,000 objects and depth 512. The local whole-source limit is 32 MiB, independently of the protocol's 8 MiB envelope and 1 MiB chunk limits and any smaller Hub deployment limit. These are resource bounds, not verification of a statement's meaning.

Reopening under the database write lock removes only owned temporary files and unregistered orphan object files. A crash after publishing a file cannot make it registered or searchable. A crash before the snapshot transaction commits leaves the old head and old index together. Registered staged objects and committed history are retained. Symlinks cannot redirect object publication or reads to an outside file.

## Search

Search text uses the Hub's deterministic tokenizer: NFKC, lowercase, adjacent Unicode letter/number/underscore pairs within each word, and isolated single characters. It uses neither `Intl.Segmenter` nor FTS trigram. Two-character Chinese words are searchable. This normalization affects only the index and query, never evidence bytes.

FTS5 receives hex-encoded tokens, not user query syntax. Searches include statements, data and UTF-8 quotations, with folder, entry type and status filters. Limits are 4,096 query bytes, 100 results per page, 1 MiB per-entry token budget and 64 MiB of encoded terms per current projection. Continuations bind the query, filters and current snapshot. A changed snapshot or query refuses the old cursor. `rebuildSearch()` derives the current projection again from the immutable snapshot.

## Local qualification and model tools

`text@1`, `json@1` and `markdown@1` are portable adaptations of the pinned Hub parsers, decoding and canonical selector codecs under Apache-2.0. Their upstream test cases and generic Markdown fixture are pinned alongside the implementation; the Hub-only sandbox input-serialization test is outside this client adaptation. `credential-scan@3` scans decoded and encoded views using the same portable scanner. Its HTML character-reference data retains its BSD notice. No other parser is installed or executed by claiming a name in a manifest.

`circle-local-verification@1` checks current conflict-free sources, exact located quotations and qualified local entry dependencies. Whitespace, case and Unicode form remain significant; empty/whitespace-only quotations cannot qualify. Raw originals and quotations retain their bytes, including BOM/CRLF and decomposed Unicode. Parser output follows that declared parser's decoding rules. Unsupported parsers and native Hub references without an authorized resolver remain incomplete, not qualified. Missing/failed reads are incomplete; a located quote mismatch is recorded separately. A verification operation inspects at most 64 MiB, caches parsed documents within that work budget, allows 100,000 nodes per parse and bounds entry-dependency depth to 100. A limit produces an incomplete observation, never success.

Observations live in a migration-2 side table keyed by snapshot, object and local rule version; they record scanner/parser versions, positions and reasons. Immutable revisions contain no local qualification flag. A new snapshot rechecks current entries and rebuilds the search status in the same transaction. The local observation proves deterministic quotation/path conditions only, never statement meaning or Hub share authority. The Hub must independently reverify.

The runtime exposes `knowledge_read` as a bounded address/schema discovery tool. Content requires explicit `snapshot` and `object` IDs. `object: "schema"` returns a paginated copy of the pinned write format without opening a store. Knowledge/memory intent or a knowledge read promotes `knowledge_search`, `knowledge_write`, `memory_write` and the currently unavailable `knowledge_share`; they stay available for that conversation. The existing curated empty-workspace prompt fixture now includes that reader and still enforces its unchanged 7,000-token ceiling; runtime tests separately check actual schema promotion. Runtime configurations with extra local/integration tools have their own additional payload. A trusted host task lock refuses search and personal writes and permits only its explicit snapshot/object allowlist. This stage provides the host port; it does not infer a Hub lock from model text.

`knowledge_write` proposes at most 64 typed revision/byte objects and 8 MiB against `expected_head`; Circle derives inventory pages and the snapshot. Revision parents must continue every current head, so moves, deletions and conflict resolutions cannot silently discard a branch. `memory_write` creates, edits, enables, disables or deletes a stable memory identity. Memory Markdown is limited to 24,000 UTF-8 bytes per document; title, path and Markdown together are limited to 48,000 bytes and 20 enabled documents. Disabled current documents use no context budget. A conflict reserves one document and the largest candidate, using the Hub's 8,000-byte path reservation when its directory is unresolved. Existing MEMORY.md is neither imported nor changed, and eligible structured memories load into the next session or after an explicit refresh.

Both writes require a person to approve the exact canonical object preview. Auto/accept-edits modes, saved rules, hook allows and model `confirm: true` cannot authorize them. A headless call cannot write. Rejection/cancellation leaves bodies, current head, search and history unchanged. After approval the database write lock rechecks the expected snapshot, then publishes the validated objects, observations, projection and head together. A changed version requires a fresh proposal and confirmation.

Credentials and bounds are checked before publication, including complete originals whose credentials could cross chunk boundaries. Rejected proposals are reduced to safe reasons before durable tool-call history/events and opaque provider replay; detector positions contain no matched text. No rejected body is put in objects, the index or temporary files. Binary or unsupported scan views have no clean conclusion and are refused by these write tools. Low-level `KnowledgeStore.put/commit` remain trusted storage/transport primitives, not model tools or a credential-acceptance API.

## Personal packs

A `pack_manifest` revision is portable manifest data only. It carries no code. `installPersonalPack` is an explicit host service requiring the current snapshot, selected local folder, existing workspace/user skill scope and a person approval callback. It compares pack.json to the revision, validates allowed/required paths, aggregate size (32 MiB), exact file sizes/hashes and credential scans, refuses symlinks and same-name skills, then installs private files under `knowledge/packs/<manifest-object>`. It never copies a folder into the automatic `skills/` root. The original selected files are unchanged. Code transfer through an authorized MCP pack entry and desktop selection remain later stages.

Installation and enable/disable are separately confirmed and recheck the current snapshot. Only current, conflict-free, enabled installations with all files intact appear in the model skill catalog. Existing built-in/user/project precedence is preserved. Disabled, changed or missing files disappear from the next model request; loading a stale catalog item also refuses. Workflow and skill kinds remain distinct metadata; local installation is not Hub validation of a locked workflow version.

`hooks.json` is not an allowed file in the pinned pack protocol and is never copied from an existing skill folder. Personal pack discovery ignores a manually added hooks sidecar too; installation never fabricates a hook approval hash. Hook import/enable has no new entry point in this stage. Existing standalone skills and their hook behavior remain compatible, with no automatic migration, scan or upload.

Native pages, packaged application validation, authorized sharing and actual test-Hub round trips belong to later stages. In local-only mode, the eventual “分享到团队…” action is disabled with a switch-to-sync explanation and entry point; there is no temporary sync or new Hub endpoint. The model share tool currently returns unavailable and performs no transfer in either mode.

## Resumable personal sync engine

`KnowledgeSync(home, transport, options)` opens only the supplied home. Its transport is `SyncHttp` bound to one explicitly selected server origin and a host-supplied Bearer provider. HTTP uses only the 12 pinned `/api/sync/v1` routes, omits cookies, refuses redirects, accepts HTTPS or loopback HTTP and bounds streamed JSON responses to 16 MiB. No model tool exposes this transport. No access/refresh token is written to the local database, pending operation, result cache or status observer. The runtime supplies those ports from the explicitly selected MCP connection, never from model arguments.

Migration 3 appends a private sync journal and a singleton lease table. The journal binds one active server/account identity, epoch, common snapshot, frozen session/cursor/descriptors, immutable pending request/digest, receipts and successful commit time. A different host binding cannot dispatch an old queue. Explicit host confirmation is required to initialize from retained local bytes after an observed epoch change or local mode; a token refresh must not change that stable identity. The client does not infer an account from a device name or credential value.

The lease uses SQLite's atomic write lock and a random fencing token, canonicalizing aliases through the store's real home. Its heartbeat is 5 seconds, expiry 30 seconds, and no PID is used for takeover. Every request checks the live fence before dispatch and after response; local journal/head/projection changes check it inside the same write transaction. A delayed or expired holder cannot renew, release its successor or advance the local baseline. Already dispatched remote work may still complete after cancellation or ownership loss; only a recovered receipt establishes its result.

The driver registers the client, opens a frozen session, persists inventory pagination, imports only complete batches with matching IDs/kinds/sizes, then merges by stable identity and revision ancestry. The common base cannot be omitted. Different identities form a union; identical or ancestor heads collapse; concurrent revisions, delete-versus-edit and directory position races retain all heads. Same-name directories and deleted ancestors with surviving children suppress dependent paths/search and produce structural conflicts without deleting content. Duplicate current entry content at the same path also remains conflicted, matching the Hub projection rule. Malformed graphs, missing identities, cycles and multiple independent roots are refused rather than renamed or discarded; the immutable local and remote branches remain stored. The engine never uses a model or timestamp to choose content. Existing confirmed revision writes resolve a conflict only by continuing every head.

Transfers obey both protocol limits and smaller server object/count/decoded-batch limits; base64 wire expansion is accounted for by the server's advertised decoded-batch budget. An operation ID, exact body and JCS request identity are durable before dispatch. Lost upload/commit/mode replies query `/operations` first; only an unavailable receipt replays the same operation and exact request. A changed payload cannot reuse its key. Expired sessions are recreated using retained local revisions and accepted objects. A CAS mismatch downloads the new frozen state and makes a new merged candidate/operation, never just changes `expected_state` on the old request.

Only a validated commit receipt advances the common base, successful timestamp, locally recomputed verification, current head and index. All commit result pages (verification, projections and conflicts) remain private journal observations, distinct from local verification; pages must keep the same receipt and state and have a bounded 64 MiB aggregate. A local edit made during HTTP remains a pending descendant. No remote qualification flag upgrades a local search result. Uploads, partial downloads, quota failures and lost replies do not advance the timestamp.

`start`/`notify` coalesce work with a 250 ms lower bound and 15-second idle polling. Network/service errors back off up to five minutes; 429 respects the larger server minimum. 401 pauses as login required without an automatic browser/login loop. Local/purging mode or a changed epoch stops the old queue; retained local bytes are unchanged. `cancel` stops scheduling and aborts local in-flight waits, retaining uncertain requests for receipt recovery. `abortTransfer` is an explicit, receipted remote session abort and retains local revisions. `close` cancels and releases resources. Mode changes call `/mode/check`, require a person callback on the exact impact preview, recheck the expected state and persist the operation before `/mode`; decline/stale/canceled previews cannot silently purge. Terminal person confirmation and global selection persistence are implemented; desktop pages remain unfinished.

Tests use a loopback synthetic protocol peer and isolated homes. They establish client state transitions and stored/network effects only, not the real Hub's authentication, purge, capacity accounting, server transactions or deployed availability. Real isolated Hub round trips remain stage 6. Native development/packaged knowledge-page acceptance remains stage 5/6.

## Selected MCP authorization

`KnowledgeConnection` accepts an existing HTTP/SSE MCP connection selected through `/knowledge connect`. Before that selection it sends no sync request to any configured service. Global `knowledge_sync` stores only its profile name and opaque binding; projects cannot replace it. Selecting a different account requires fresh person approval before retained local revisions can upload. Direct Bearer headers reuse their existing secret/environment references. Replacing a direct credential changes the binding.

OAuth uses the existing private `mcp-auth.json`, official MCP SDK discovery/PKCE and token refresh. Ordinary MCP traffic and sync share one refresh in flight per grant, with a private cross-process lock and a second token read after acquiring it. Rotating and nonrotating refresh tokens are both supported. A refresh keeps the opaque grant identity; an explicit login creates another. The background path uses cached discovery only: no registration, browser, discovery fallback or login loop. Failed refresh pauses as login required. `/knowledge login` explicitly forgets the old grant and invokes the original MCP login; select the new account again afterward. A same-grant token repaired externally can resume with `/knowledge sync`.

Logout, credential replacement, disabled/changed configuration and disconnect stop the old client; before accepting responses the host checks the binding again. Loaded team preferences are removed from the current session on authorization loss/disconnect. An already-dispatched remote operation may still finish; the durable journal recovers its receipt. Only the local host sees credentials, never the knowledge database, model prompt, renderer or sync status. Refresh has a 30-second deadline and last-waiter cancellation; canceling one shared waiter leaves other callers alive.

## Session preferences

Preparation reads the selected trusted read-only `get_nodes` tool's team `memory` branch with `for_session: true`. It freezes list and document versions across all pages. Only enabled, auto-load-allowed team documents are accepted; shared personal spaces are excluded. A changed/stale/malformed page discards the complete team snapshot with an unavailable notice, while eligible local personal preferences can still load. Local disabled/deleted/conflicted memories and unresolved directory paths are excluded. Credentials are scanned after chunks are assembled, including titles/paths and the selected connection's current credentials.

The actual model request orders team preferences, personal preferences, then existing instruction/memory files. Structured preferences are explicitly scoped below user/project instructions, escaped and described as preferences rather than evidence, task inputs or executable instructions. Team plus personal content is capped at **48,000 UTF-8 bytes including escaped text, titles, paths, wrappers and omission/status text**, further reduced to fit the complete model request's input budget. Truncation respects UTF-8 and escape boundaries and reports omitted bytes/documents. Existing files retain their 24,000-byte per-file cap and normal context handling; they are not migrated or uploaded. The empty prompt/tool ceiling is unchanged.

A loaded snapshot does not change mid-session when local or remote revisions change. A new session, reload or idle `/memory refresh` prepares another snapshot; authorization loss removes team content immediately. `localContext: false` loads none and starts no sync. Headless runtimes without integrations load eligible local preferences only. `/memory loaded` displays the actual bounded structured context, while `/memory team` browses the frozen eligible team documents.

## Terminal commands and current limits

`/knowledge` uses existing pickers and status surfaces. It supports list/search/read, a bounded explicit UTF-8 source import, revision history, conflict candidate selection, statement edits, directory/source rename and moves, deletion, connection selection, explicit sync/login and checked mode changes. Every content write, conflict resolution, connection selection and destructive mode change asks the person, including in auto mode; a changed local head or mode impact requires a fresh preview. Imported sources preserve original bytes and have no invented verified statement. Import reads one available workspace file of at most 1 MiB and never imports MEMORY.md automatically; malformed UTF-8, credentials and outside paths are refused.

`/memory personal`, `write <title> | <text>`, `edit <number> <text>`, `enable`, `disable` and `delete` manage structured preferences with the same person-only confirmation/CAS checks. Original bare `/memory`, `add [account]` and `remove` remain file operations. Rejected proposed text is not added to terminal input history. Team/loaded/refresh inspect the frozen snapshot and its real bounded prompt. The terminal remains English on both palettes. Desktop commands currently disclose that the new pages are unavailable and direct the person to the terminal; stage 5 supplies those pages.
